# Boot-work baseline for `make check-perf-baseline-disk`.
#
# The machine: -smp 1 -m 1G -drive file=target/perf-baseline-disk.img,if=none,id=nvme0,format=raw -device nvme,drive=nvme0,serial=protofire -netdev user,id=net0 -device virtio-net-pci,netdev=net0 [features: demo-disk perf_baseline fs_profiler net_profiler alloc_profiler fault_profiler].  A baseline describes one shape, so the check
# refuses a boot whose shape does not match this line.
#
# One row per counter the boot prints: `key baseline tolerance`.
# Tolerance is absolute: the counters a boot is still moving when it
# samples (heap, DHCP traffic) drift by scheduling jitter, and the ones
# that stopped at boot do not drift at all.  Re-record with
# `sh scripts/check-perf-baseline.sh --record`, which keeps every
# tolerance that is already written down.
#
# The `fs-*` rows are the counters a filesystem keeps: how many
# operations it served (`fs-reads`, `fs-writes`) and how many bytes
# those operations were asked for (`fs-read-bytes`, `fs-write-bytes`),
# summed over the mounted volumes.  What a cache served or a device
# moved is not counted here.  The `cache-*` rows are the block
# caches of those volumes summed — hits, misses, prefetches issued and
# sequential hits, evictions — and the `blk-*` rows are what actually
# reached a device, counted where a device enters the filesystem
# (`src/kernel/block.rs`).  Three heights, one read.  The last of
# those rows, `blk-in-flight-high-water`, is the most requests that
# were ever outstanding at once: one says every device the boot used
# completes in place, which is the number an asynchronous interface
# would have to beat before it is worth having.
#
# The `wl-*` rows are the defined storage workload's own share of that
# work, counted as deltas around the run (`src/kernel/workload.rs`):
# what a filesystem, a cache and a device did for a fixed set of writes
# and reads rather than for the boot as a whole.
# `wl-device-bytes-per-asked-byte` is the ratio between the two — the
# write amplification of one named workload.  Its duration is printed on
# a line of its own and is deliberately not recorded here.
# `ticks` and `irqs` moved too, from 560/582 to 534/556, and that is the
# same window the other baselines describe: the summary is printed by the
# maintenance thread, which wakes every 25 ticks, so the row records
# where inside that window the boot happened to be — and this host is
# currently reaching it about 26 ticks earlier than when the row was
# written.  Nothing in the tree changed to cause it: the commit before
# this work measures the same 534.
#
# One more thing recording this found: the read path itself jitters by a
# block.  Across nine runs on this host `fs-reads` came back 841 six
# times and 840 three — one 512-byte block that a boot sometimes finds
# in the cache and sometimes does not, with `fs-lookups`,
# `cache-hits` and `cache-sequential-hits` moving with it by one.
# Those five rows carry a ±1 (and ±24 bytes, one block) tolerance for
# that reason, and only they do: `blk-reads` and every `wl-*` row were
# identical in all nine, which is what says this is a cache hit at the
# margin rather than the boot reading something extra.
#
