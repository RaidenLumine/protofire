# Kernel module dependency edges: the census scripts/check-layering.sh
# ratchets.
#
# Each row is `<from module> <to module> <occurrences>`: how many times a file
# belonging to `<from>` names `<to>` in code (line comments stripped,
# self-references skipped).  A module's files are `src/kernel/<from>/` (or
# `src/kernel/<from>.rs`), except for the five subsystems that live at the
# crate root — `fs`, `memory`, `network`, `drivers`, `syscall` — whose files
# are `src/<from>/` and which are named `crate::<from>::` rather than
# `crate::kernel::<from>::`.  Both spellings count as edges.  The gate fails
# when a count rises, when a row shrinks without the census being re-recorded,
# or when the tree has an edge no row mentions — so a new dependency between
# two modules has to be added here on purpose.
#
# Re-record with `sh scripts/check-layering.sh --record` in every change that
# moves an edge.
#
# Two directions are wrong on purpose and are expected to reach zero:
#
#   * `block` naming anything above `sync` — it is the layer the disk drivers
#     and the filesystem both build on, so it must stay at the bottom.  The
#     one row it has is the leaf mutex, which is where the bottom is.
#   * `drivers` naming `fs` — a driver hands a found device over through
#     `kernel::block::publish_device`; it does not know who consumes it.
#
# `process` <-> `sync` and `process` <-> `smp` are gone: `sync` is now a leaf
# that names no thread, and the per-CPU scheduler table lives in the scheduler.
# Since `sync` holds only a spinlock and the mutex wrapper over it, naming it
# is naming the bottom layer.
#
# The occurrences of `drivers` naming `process` and `sync` are argued rather
# than counted as debt: each PCIe driver owns a wait queue for its own device's
# completion interrupt — `virtio_net` for its queues, the block driver for its
# request queue — the same shape `serial`, `keyboard` and `mouse` already have
# for theirs.  The wakeup belongs to the device whose identities were claimed,
# so it cannot be folded into a platform-wide signal, and two devices claiming
# theirs is the point of the second driver rather than duplication of the
# first; see §13 of code-style.md.
#
# `perf_baseline` names `fs`, `memory`, `network`, `irq_stats` and `block` on
# purpose: it is the boot-work summary, and the counters it prints are kept by
# the subsystems that do the work — including the three heights a read is
# counted at (the filesystem's own operations and bytes, the block cache's
# hits and misses, and what reached a device, which is `block`'s).  The edges
# point one way — the observer depends on what it observes, and nothing
# depends on the observer but `maintenance`, which calls it — so these rows
# are the shape of the check, not a cycle to cut.  The `fs` -> `block` rows
# beside them are that direction spelled out: `src/fs/mod.rs` re-exports the
# block layer's interface, and the counted occurrences are the three places a
# device is handed to the wrapper the boot-work line reads.
#
# `fs` no longer names `process` either.  Its one edge was the anonymous
# pipe's condition variable, and a pipe that parks a thread is not storage:
# it is an IPC endpoint that borrows the `VNode` interface, so it moved to
# `kernel::ipc` and the dependency now points `ipc` -> `fs` instead.
#
# What is left has one shape.  `process` names its consumers — `memory`,
# `syscall`, `network`, `fs`, `percpu`, `drivers` — for file handles, sockets,
# counters, and caches; and those consumers name `process` back for the two
# things only it has: a thread to run on and a way to block.  `memory` <->
# `fs`, `fs` <-> `service`, and `fs` <-> `kernel_log` are the same story at a
# lower altitude.  Each row is the finish line for its cut; a cut is done when
# its rows reach zero and the census is re-recorded.
#
# One module is a diagnostic rather than a layer: `vm_churn` exists to stress
# the stack window and the invalidation log, so it names `memory`, `process`,
# and `smp` on purpose — its rows are the number of structures it drives, not
# a layering direction.
#
# `service` names `fs` and `crypto` for one reason: a service declaration is a
# file, and a service's origin is that file plus the digest of its bytes.  The
# boot path and `service_declare` share one reader, so the pair is two rows
# rather than a new direction: the service manager has always read the
# declarations it runs.
#
# `device` names `sync` because the device ledger is a registry, and the boot
# names `device` because that is where the drivers' findings are published —
# `drivers` does not name `device`, which would close a cycle with the
# `device` -> `drivers` row the virtual devices' handlers come from.
#
# The same shape one level lower: `drivers` names `sync` for the registry the
# probes record into (a `drivers` -> `sync` row the module already had), and
# the boot names `drivers` to publish that registry, the way it names `device`
# to publish the ledger.  Nothing here reaches a consumer: the probe writes,
# the boot reads, and the filesystem's registry is written by the boot.
#
# The device ledger is a *view* rather than a copy: `device` asks `drivers` for
# what the probes bound — a direction it already had, for the virtual devices'
# handlers — and names them for `/dev`.  So the boot no longer names `drivers`
# to publish anything (`mod` -> `drivers` is back to one row) and `device` holds
# no registry of its own (its `sync` row is the test lock alone).
#
# Two rows are *tests*, not layering: `fs` -> `drivers` is devfs's own tests
# populating the registry their view reads, and `drivers` -> `sync` carries that
# registry's test lock.
#
# A declaration is only read from a path whose components are the directory
# entries they claim to be, so the service manager names `fs` a handful more
# times — the walk itself — in the direction it already had, since it reads the
# declarations it runs.
#
# The install syscall names `fs` once more, to resolve the path it is handed
# against the caller's working directory.  Everything else it does — reading the
# package, writing `/apps` — it does through `user::program`, which is where the
# install path lives; the syscall is the way in, not a second implementation.
#
# The audio node's mode moved two rows, both in directions the rows already
# had.  `device` names `fs` twice more because a device node's mode is a
# security descriptor: the ledger is the filesystem's view of the devices, and
# the one node that is writable by any user is the one that has to say so in
# the filesystem's own terms.  `syscall` names `fs` once more for the same
# descriptor, resolving what it was handed into an access mode — the same
# direction as the path walk beside it.  Neither is a new direction, and the
# rows above for `device` -> `fs` and `syscall` -> `fs` are where this one is
# counted.
#
