# Boot-work baseline for `make check-perf-baseline-smp`.
#
# The machine: -smp 4 -m 1G -netdev user,id=net0 -device virtio-net-pci,netdev=net0 [features: demo-disk perf_baseline fs_profiler net_profiler alloc_profiler fault_profiler].  A baseline describes one shape, so the check
# refuses a boot whose shape does not match this line.
#
# One row per counter the boot prints: `key baseline tolerance`.
# Tolerance is absolute: the counters a boot is still moving when it
# samples (heap, DHCP traffic) drift by scheduling jitter, and the ones
# that stopped at boot do not drift at all.  Re-record with
# `sh scripts/check-perf-baseline.sh --record`, which keeps every
# tolerance that is already written down.
#
# The counters a second CPU adds are the ones this shape has and the
# single-CPU record does not: the AP wake-ups, the per-CPU tick, and
# the IPIs a TLB shootdown sends.  `ipis` moves by a count or two with
# the schedule, so it carries a tolerance here that the one-CPU
# baseline, where it is identically zero, does not need.
#
# The `fs-*` rows are the counters a filesystem keeps: how many
# operations it served (`fs-reads`, `fs-writes`) and how many bytes
# those operations were asked for (`fs-read-bytes`, `fs-write-bytes`),
# summed over the mounted volumes.  What a cache served or a device
# moved is not counted here.  The `cache-*` rows are the block
# caches of those volumes summed — hits, misses, prefetches issued and
# sequential hits, evictions — and the `blk-*` rows are what actually
# reached a device, counted where a device enters the filesystem
# (`src/kernel/block.rs`).  Three heights, one read.  The last of
# those rows, `blk-in-flight-high-water`, is the most requests that
# were ever outstanding at once: one says every device the boot used
# completes in place, which is the number an asynchronous interface
# would have to beat before it is worth having.
#
# The `wl-*` rows are the defined storage workload's own share of that
# work, counted as deltas around the run (`src/kernel/workload.rs`):
# what a filesystem, a cache and a device did for a fixed set of writes
# and reads rather than for the boot as a whole.
# `wl-device-bytes-per-asked-byte` is the ratio between the two — the
# write amplification of one named workload.  Its duration is printed on
# a line of its own and is deliberately not recorded here.
#
# RFC 0029 adds one thread to this shape: `kernel-net-rx`, which drives
# the device while a socket has a parked receiver.  `frames` rises by one
# and `frame-zero-bytes` by 32768 — its kernel stack — and `frame-frees`
# rises with it, because the thread is placed on the boot CPU and the
# boot's own stack accounting is what changes.
#
# Its placement is why `ipis` did not move.  The thread's cadence while
# somebody is waiting is one tick, and the tick is the boot CPU's timer;
# spawned by the round-robin rule it landed on another CPU and every one
# of those wakeups was a reschedule IPI — measured at 58 to 74 against
# the 51 this row records.  Placed on the boot CPU it is woken where the
# tick runs, and the row came back to 51-53.
#
# None of it is periodic either way.  With no waiter the thread blocks
# on the UDP table's receive event rather than on a timer, so a machine
# where nobody resolves produces no wakeups at all.
#
# The DNS self-test is compiled out of this shape (`perf_baseline`), so
# these counters describe the product rather than a boot's proof of it;
# `make check-x8664-runtime` runs the proof.  `ip4-rx`/`ip4-tx` moved for
# the reason they also moved in the single-CPU baseline: DHCP's exchange
# is one of the things this shape measures, and it is not deterministic.
#
