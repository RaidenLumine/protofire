# Boot-work baseline for `make check-perf-baseline`.
#
# The machine: -smp 1 -m 1G -netdev user,id=net0 -device virtio-net-pci,netdev=net0 [features: demo-disk perf_baseline fs_profiler net_profiler alloc_profiler fault_profiler].  A baseline describes one shape, so the check
# refuses a boot whose shape does not match this line.
#
# One row per counter the boot prints: `key baseline tolerance`.
# Tolerance is absolute: the counters a boot is still moving when it
# samples (heap, DHCP traffic) drift by scheduling jitter, and the ones
# that stopped at boot do not drift at all.  Re-record with
# `sh scripts/check-perf-baseline.sh --record`, which keeps every
# tolerance that is already written down.
#
# The `fs-*` rows are the counters a filesystem keeps: how many
# operations it served (`fs-reads`, `fs-writes`) and how many bytes
# those operations were asked for (`fs-read-bytes`, `fs-write-bytes`),
# summed over the mounted volumes.  What a cache served or a device
# moved is not counted here.  The `cache-*` rows are the block
# caches of those volumes summed — hits, misses, prefetches issued and
# sequential hits, evictions — and the `blk-*` rows are what actually
# reached a device, counted where a device enters the filesystem
# (`src/kernel/block.rs`).  Three heights, one read.  The last of
# those rows, `blk-in-flight-high-water`, is the most requests that
# were ever outstanding at once: one says every device the boot used
# completes in place, which is the number an asynchronous interface
# would have to beat before it is worth having.
#
# The `wl-*` rows are the defined storage workload's own share of that
# work, counted as deltas around the run (`src/kernel/workload.rs`):
# what a filesystem, a cache and a device did for a fixed set of writes
# and reads rather than for the boot as a whole.
# `wl-device-bytes-per-asked-byte` is the ratio between the two — the
# write amplification of one named workload.  Its duration is printed on
# a line of its own and is deliberately not recorded here.
#
# `ticks` and `irqs` are printed by the boot and deliberately not
# recorded here.  They say *when* the sample was taken — the boot
# prints it once it has stopped doing storage work, so they measure
# how fast the host got there.  A baseline compares work, and a row
# that moves with the host is the one thing it must not compare.
#
# The DNS self-test runs in this build on purpose, and its three
# kernel threads are part of the frame rows: `kernel-net-rx` drives
# the device while a socket has a parked receiver, and the self-test
# spawns a waiter and an injector that walk the resolver's wait path
# once (RFC 0029).  `frame-zero-bytes` grows by one 32 KiB stack per
# thread; the two self-test threads terminate, so `frame-frees` grows
# with them and the receive thread's stack does not come back.
#
# The numbers below were re-recorded at 0.8.13+, and the reason is
# named here rather than left to a reader diffing the file, because a
# re-record that explains nothing is indistinguishable from a gate
# widened to pass.  Bisected with `git bisect run` over the 79 commits
# since the previous recording (f3e82ec), and reproduced 3 of 3 boots
# at each step, so neither number is jitter:
#
#   4a5ee57  "Let a fork resume on the stack it was forked from"
#            steps the six I/O rows up together — `fs-reads` 1455 ->
#            1465 and its bytes, cache hits/prefetches/sequential-hits
#            and `blk-read-bytes` with it.  Fork became reachable from
#            the console in this range, and the console boot now runs a
#            fork the recorded boot did not; the reads that move are the
#            child's image being faulted in.  This is the boot doing
#            more work, not the counter changing what it counts.
#
#   8d95bda  "Give the software page table a process identity" raises
#            `heap-bytes` by ~10.9 MB (26.7 MB -> 37.6 MB).  The
#            content store went from one table for the machine to one
#            keyed by address space, and `store_page_content` keeps a
#            4 KiB `Vec` per evicted page; ~2660 pages is the gap.  It
#            is an allocation the change added on purpose — the
#            alternative was two processes sharing entries — so the row
#            moves with the design rather than with the host.
#
# `heap-bytes` is cumulative bytes allocated, not live bytes, so it
# never falls; its 262144 tolerance is the boot's own jitter around
# the sample point, measured at 278 KB across three boots, and is not
# wide enough to hide either number above.
#
