# RFC 0003: Program a device's MSI-X table on x86_64

- **Status:** Superseded
- **Author(s):** Raiden Lumine <2557597107@qq.com>
- **Date:** 2026-10-06
- **Supersedes:** none

## Summary

> **This RFC was superseded by
> [RFC 0005](0005-claim-the-msix-entries-a-driver-names.md)**, which keeps its
> decision to program a device's own MSI-X table and its own IDT vector window,
> and changes the *size* of a claim: one identity per entry the driver names
> rather than one per entry the table has.  The rest of this document is the
> record of the decision it made, including the fallback handler that change
> removes.

Every PCIe device on x86_64 today signals through its legacy INTx line, which
this kernel never wires, so every completion is polled.  This RFC programs a
device's own MSI-X table with messages this machine composes, allocates the
vectors from a window of the IDT that gets its own stubs, and answers a
delivered vector from the same handler registry the ITS and the IMSIC already
use.  A driver claims its vectors at probe time, the platform programs the
table once the LAPIC is up, and the completion path parks on the interrupt
only after that.

## Motivation

The message-signalled path has two claimants on the device-tree machines and
none on x86_64.  [docs/status.md](../status.md) records both halves: in the
interrupt census, "on x86_64 the composition and the vector numbers are there
and no device's table is programmed, which is why that machine's PCIe devices
poll"; and in the driver census, only "on the two PCIe machines [are the NIC's]
queues interrupt-driven", with x86_64 left with "no MSI-X claim path, so a
transmit polls for its completion".

RFC 0001 left that out of scope deliberately, with the reason written down: "a
message-signalled interrupt's destination is part of the message, the message
lives in the device's own table, and `src/arch/x86_64/msi.rs` is where this
kernel composes one.  Placement there belongs to whatever programs that table,
and changing it afterwards is a different change."  This is that change.

It is not only the NIC: NVMe has vector constants and an acknowledge handler
and no programming path (`src/drivers/nvme.rs`), and xHCI has no interrupt
path at all.  Each of them polls because there is nothing that can program a
table.

## Current state

- **Composition.**  `src/arch/x86_64/msi.rs` composes the address
  (`0xFEE0_0000 | apic_id << 12`) and the data word (vector, delivery mode),
  and builds a `MsixTableEntry` that starts masked.  Nothing writes one.
- **The table.**  `src/arch/pci/mod.rs` parses the MSI-X capability into
  `MsixCapability` — message control, the table's BAR indicator and offset,
  the PBA's — and `pci_capability_msix` reaches it on every machine.  What is
  missing is a mapper from the table's BAR to a virtual address on x86_64 and
  a writer of table entries.
- **Vectors.**  `src/arch/x86_64/interrupts.rs` names vectors as constants
  (timer 32, keyboard 33, NVMe 44-45, VirtIO 46-47) and `handle_irq` matches
  on them.  `src/arch/x86_64/idt/types.rs` has one stub per vector only for
  vectors 0-49 (`EARLY_HANDLERS`); everything above that reaches
  `interrupt_stub_default`, which reports vector **255** for all of them, so a
  vector outside that range cannot be told apart from another.
- **The registry.**  `src/arch/irq_handlers.rs` already holds "one handler per
  identity, a first-fit allocator over a window, and a lookup that runs the
  handler an arriving message names".  RISC-V calls it with its IMSIC
  identities, AArch64 with LPI numbers.  x86_64 does not use it.
- **The driver's half.**  `src/drivers/virtio_net.rs` already owns a wait
  queue per queue, parks on it when `DeviceInterrupts::is_armed()` and polls
  when it is not.  On x86_64 that path is dead code: the machine never hands
  the driver a `DeviceInterrupts` at all.
- **End of interrupt.**  Both controllers are told through
  `interrupt_controller::end_of_interrupt`, which the LAPIC path already
  handles for line interrupts.

## Design

**Vectors come from a window, and a vector is the identity.**  The MSI-X
vectors are a fixed window of the IDT — `MSIX_VECTOR_BASE..=MSIX_VECTOR_LAST`,
chosen inside the free range the vector comment already reserves (34-127) and
above the fixed assignments.  That window gets its own stubs, generated by the
same `ISR_NOERR` macro that generates the others, and its own IDT gates.  The
dispatcher then answers a vector in the window by looking it up in
`irq_handlers` with `base = MSIX_VECTOR_BASE`, the call the other two machines
already make.  One registry, three sources of identity.

**A claim is a table entry per vector, taken at probe time.**  A driver asks
the platform for a claim the way it does on the other machines:
`arch::platform::pci_claim_msix(window, named, fallback)` answers a
`DeviceInterrupts`.  The claim allocates `count` consecutive vectors with
`claim_each`, so each named entry gets the handler for its queue and every
other entry of the device's table gets the device-wide one.  Identity 0 is not
an interrupt name here either, so "not armed" and "no identity" stay
distinguishable.

**The platform programs the table, and only when the machine can receive.**
The claim records the function, the BAR the table lives in, the table's offset
and size, and the vectors.  Arming is deferred exactly as on AArch64 and
RISC-V (`defer_msix_arming`): the table's entries are written masked, and the
unmask happens with the machine's interrupt controller up.  A device whose
table cannot be reached — a BAR above the range the kernel maps, a function
with no MSI-X capability — leaves the driver on the polling path it has today,
which is what the driver's `is_armed` check already expresses.

**Placement is round-robin over the CPUs that can receive, as RFC 0001
decided.**  On x86_64 the destination is the APIC id in the message address,
so the same rule is a different store: entry *i* names the APIC id of the
*i*-th online CPU.  This is the part RFC 0001 deferred here, and it is decided
together with the programming rather than left to a later rewrite of a table
that is already live.

**A vector is one queue's, and the wakeup belongs to that queue.**  The
registry hands each entry the handler the driver named for it, so a completion
wakes the queue that caused it — the same claim the PCIe machines make, and
the reason `claim_each` exists.

**What a driver does with it does not change.**  `DeviceInterrupts` grows an
x86_64 arm, and the driver's existing completion path — park on the interrupt
when armed, re-read the ring either way — starts working on this machine
without a per-machine copy.

## Alternatives

- **Program the table with the constants that already exist** (46-47 for
  VirtIO).  Cheapest, and it would prove the mechanism.  It loses because a
  constant is one identity per device, not one per queue, so the wakeup cannot
  say which queue completed; because two devices of the same class in one
  machine collide on the same vector; and because it puts device assignment in
  a header the driver cannot see.
- **Add more constants and more `match` arms.**  The same collision, one
  vector at a time, and it keeps the driver's identity out of the driver's
  hands.  It is what the tree would accrete if this RFC were rejected.
- **Extend `EARLY_HANDLERS` to 256 and keep `handle_irq`'s match.**  The
  stubs have to exist either way; what loses is the *lookup*.  A 256-arm match
  is the same table `irq_handlers` already keeps, written worse, and it cannot
  tell the driver "the vector you named is taken".
- **Let each driver program its own table.**  Rejected: the composition, the
  BAR mapping and the EOI are the machine's, and three copies of the sequence
  is how the AArch64 and RISC-V halves would drift apart.
- **Enable MSI-X at boot for every function that has it.**  Rejected: a device
  whose table is programmed with a vector nobody owns stops signalling on its
  legacy line and delivers an unclaimed vector instead — worse than polling.

## Drawbacks

- **Vectors become a scarce resource with an owner.**  The window is finite
  and first-fit, so a machine with many MSI-X functions can run out; the claim
  answers `NoSpace`, and the caller stays on its polling path.
- **A device that cannot be reached gets no interrupt.**  That is by design,
  but it means "MSI-X present" and "MSI-X usable" differ, and the difference
  is only visible in the claim's answer.
- **The IDT grows.**  A window of stubs is a few hundred bytes of text and the
  gates to go with it.
- **Two delivery paths to keep honest.**  Line interrupts and MSI both end at
  `handle_irq`; the difference is which identity the message names, and every
  future device driver has to be written to the registry's shape rather than
  to a constant.

## Compatibility and migration

Nothing on disk, on the wire or in the ABI changes.  The device-tree machines
are untouched: this is a new arm of `arch::platform`'s two functions and a new
module under `src/arch/x86_64/`.  A driver that does not ask for a claim keeps
polling, and a machine whose device cannot be reached keeps polling, so the
change is never half-applied in a way that loses interrupts: the table is
written only after a claim succeeded, and unmasked only when the LAPIC can
receive.  The fixed constants for the timer, the keyboard and the stray
NVMe/VirtIO uses stay where they are; moving those to the registry is a
follow-up per device, not part of this decision.

## How this is proven

- `make check-x8664-runtime` boots with `virtio-net-pci` and asserts the claim
  (`[virtio-net] device interrupts claimed: irq ...`), the table's programming
  (`[msix  ] MSI-X on 00:02.0 delivers vectors ... on cpus [...]`), and that a
  queue's own MSI arrived (`[virtio-net] RX MSI (irq ...)`, which is a handler
  the kernel ran because a device wrote the message this machine composed).
  The placement itself is printed per entry; the stronger check — that the CPU
  serving a queue's MSI is the one its entry named — is the AArch64 check's,
  because that smoke runs two CPUs and this one runs a single CPU.
- The same check attaches a USB host controller beside the NIC, so x86_64 has
  a **second** claimant of the kind this decision was about: xHCI's table has
  sixteen entries, it claims one identity per entry, and a key pressed on the
  USB keyboard through QEMU's monitor raises the controller's own interrupt —
  the first thing on this machine that proves the window, the stubs and the
  registry answer more than one driver.
- Unit tests in `src/arch/x86_64/msi.rs` for the vector window's bounds and
  the entry composition: the window lies inside the free range and above the
  fixed assignments, it is closed at both ends, every vector in it has a stub,
  an entry is written masked, and its data word names the vector while its
  address names the destination APIC id.
- `make check-unsafe-comments`, `make clippy` and `make clippy-targets` cover
  the new MMIO writes and the stubs.
- The existing polling path is the control: a boot with the driver's claim
  refused (no MSI-X capability, or a table that cannot be mapped) must still
  complete, which `make check-x8664-runtime` exercises on every run that has
  no such device.

## Unresolved questions

- **Should the window be per-machine sized from the number of online CPUs, or
  fixed?**  Fixed is simpler and what this RFC assumes; a machine with more
  MSI-X functions than the window holds falls back to polling per claim rather
  than failing.
- **Do the NVMe and xHCI vectors move into the registry in the same change?**
  They are not required for this decision and each is its own follow-up;
  NVMe's acknowledge handler and xHCI's absence of one are why they are
  separate.
- **Is round-robin the right placement for a queue that a driver pins to one
  CPU?**  RFC 0001 chose round-robin for the device-tree machines and this RFC
  matches it, but a driver that knows its queue's CPU could do better; nothing
  in the interface forbids it later.
